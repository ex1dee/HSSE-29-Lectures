## 1. Технологический стек и инфраструктура

- **Движок сканирования:** ClamAV.
    
- **Взаимодействие с движком:** xyz.capybara.clamav-client
    
- **Брокер сообщений:** RabbitMQ (микросервисная архитектура).
    
- **Изоляция (Docker):** Контейнер ClamAV не публикует порты во внешнюю сеть (`ports` исключены). Используется инструкция `expose: 3310` для доступности только внутри внутренней сети Docker.
    
- **Безопасность ресурсов:** Настройка защиты от zip-бомб, установка таймаутов на чтение/запись, жесткие лимиты на RAM (Docker Limits).
	  
- **Кэширование**: Redis
	
- **Синтаксический/структурный анализ**: Tika

---

## 2. Организация очередей и обработка ошибок

## Очереди RabbitMQ

1. **antivirus.tasks.queue** Очередь для заданий на сканирование (отправляется приложением).
    
2. **antivirus.results.queue:** Очередь для результатов обработки (прослушивается приложением для запуска бизнес-логики).
    

## Отказоустойчивость

- **Retry Policy:** Параметр `Max Retries = 3`.
    
- **Dead Letter Queue (DLQ):** При превышении лимита ретраев сообщение перемещается в DLQ, а файлу присваивается статус `file_status = FATAL`.

## 3. Логика проверки и фильтрация

### Этапы проверки

1. **FastScan** (поверхностный синтаксический анализ):
    
    - Анализ **Magic Bytes** (первых байтов файла) для определения реального типа файла и сверки с расширением.

2. **StructuralScan** (глубокий структурный анализ, если файл размером <= 100 МБ) 
	
	- Отсекает файлы, непригодные для DeepScan, и зип-бомбы.

2. **DeepScan** (сигнатурный анализ):
    
    - Глубокое сканирование содержимого через ClamAV.
        

- **Ограничение:** Файлы более 100 МБ не проходят глубокую проверку.

## 4. Модель данных и статусы в БД

## file_status (Жизненный цикл)

Основная цепочка: `READY` -> `PENDING` -> (`ERROR` | `FATAL` | `READY`) -> `DANGEROUS`.

## scan_verdict (Результат анализа)

- **UNKNOWN:** В процессе сканирования.
    
- **ERROR:** Техническая ошибка (после исчерпания всех попыток в RabbitMQ).
    
- **TOO_LARGE**: Слишком большой размер 
	
- **PASSWORD_PROTECTED**: Запароленные файлы (архивы, документы)
	
- **EMPTY_FILE**: Пустой файл
	
- **CLEAN:** Угроз не обнаружено.
    
- **CONTENT_MISMATCH**: Несовпадение указанных mimetype/расширения с действительным mimetype. Поведение то же, что и при INFECTED, но отображается по-другому. (+ может быть и то, что mimetype просто невалидный, это надо учесть в сообщении на фронте)
	
- **RESOURCE_EXHAUSTED**: Зип/XML бомба или просто исчерпание ресурсов Tika
    
- **INFECTED:** Обнаружена угроза (в базе кэша или через Deep check).

### Категории вердиктов

- **Опасный файл:** 
	Протокол ниже
	- `INFECTED`
	- `CONTENT_MISMATCH`
	- `RESOURCE_EXHAUSTED`

- **Подозрительный файл:**
	Запрещаем предпросмотр, предупреждаем пользователя
	- `ERROR`
	- `PASSWORD_PROTECTED`
	- `TOO_LARGE`

- **Чистый файл**:
	- `CLEAN`
	- `EMPTY_FILE`

## 5. Протокол действий при обнаружении критических угроз

1. **Физическое удаление:** Объект немедленно удаляется из S3-хранилища.
    
2. **Обновление БД:** Запись о файле сохраняется в базе, но `file_status` меняется на `DANGEROUS`.
    
3. **Оповещение:** Отправляется почтовое уведомление пользователю (+говорим, что файл скоро удалится)
    
4. **Автоочистка:** Сервис очистки автоматически удаляет запись о зараженном файле из БД через 30 дней.

## 6. Ошибки при взаимодействии с антивирусом

- Если файл завис в вердикте `UNKNOWN`, то ставим вердикт `ERROR` и логируем.
- В любом случае, при `ERROR` пишем юзеру, что файл не прошел автоматическую проверку и может быть опасен и отправляем письмо на почту.
