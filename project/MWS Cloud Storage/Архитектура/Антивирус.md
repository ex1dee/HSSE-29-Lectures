## 1. Технологический стек и инфраструктура

- **Движок сканирования:** ClamAV.
    
- **Взаимодействие с движком:** Передача данных через TCP-сокет по протоколу `INSTREAM`.
    
- **Брокер сообщений:** RabbitMQ (микросервисная архитектура).
    
- **Изоляция (Docker):** Контейнер ClamAV не публикует порты во внешнюю сеть (`ports` исключены). Используется инструкция `expose: 3310` для доступности только внутри внутренней сети Docker.
    
- **Безопасность ресурсов:** Настройка защиты от zip-бомб, установка таймаутов на чтение/запись, жесткие лимиты на RAM (Docker Limits).

## 2. Организация очередей и обработка ошибок

## Очереди RabbitMQ

1. **scan-tasks:** Очередь для заданий на сканирование (отправляется приложением).
    
2. **scan-results:** Очередь для результатов обработки (прослушивается приложением для запуска бизнес-логики).
    

## Отказоустойчивость

- **Concurrency:** Лимит на количество одновременно сканируемых файлов в RabbitMQ (Prefetch count): от 1 до 3.
    
- **Retry Policy:** Параметр `Max Retries = 3`.
    
- **Dead Letter Queue (DLQ):** При превышении лимита ретраев сообщение перемещается в DLQ, а файлу присваивается статус `file_status = FATAL`.

## 3. Логика проверки и фильтрация

## Предварительная фильтрация

Проводится на стороне монолита перед отправкой в очередь:

- Директории и файлы размером 0 байт помечаются как `SKIPPED`.
    
- Архивы с паролем не проверяются глубоко; пользователю выводится уведомление: "Мы не смогли проверить этот файл на вирусы, скачивайте на свой страх и риск".
    

## Этапы проверки

1. **Fast check** (для архивов с паролем и файлов > 10 КБ):
    
    - Проверка хэша по локальной базе результатов (`scan_results_cache`).
        
    - Анализ **Magic Bytes** (первых байтов файла) для определения реального типа файла и сверки с расширением.
        
2. **Deep check** (для файлов до 100 МБ):
    
    - Глубокое сканирование содержимого через ClamAV.
        

- **Ограничение:** Файлы более 100 МБ не проходят глубокую проверку.

## 4. Модель данных и статусы в БД

## file_status (Жизненный цикл)

Основная цепочка: `READY` -> `PENDING` -> `SCANNING` -> (`ERROR` | `FATAL` | `INFECTED`).

- В статусе `SCANNING` запрещено скачивание файла, но разрешено его удаление и редактирование метаданных.
    

## scan_result (Результат анализа)

- **UNKNOWN:** В процессе сканирования.
    
- **ERROR:** Техническая ошибка (после исчерпания всех попыток в RabbitMQ).
    
- **SKIPPED:** Проверка не требовалась (пустые файлы/папки).
    
- **CLEAN:** Угроз не обнаружено.
    
- **CONTENT_MISMATCH:** Несоответствие Magic Bytes заявленному расширению.
    
- **INFECTED:** Обнаружена угроза (в базе кэша или через Deep check).
    

## scan_level (Глубина проверки)

- `NONE`
    
- `FAST`
    
- `DEEP`

## 5. Протокол действий при обнаружении вируса (INFECTED)

При получении статуса `INFECTED` система выполняет следующие шаги:

1. **Физическое удаление:** Объект немедленно удаляется из S3-хранилища.
    
2. **Обновление БД:** Запись о файле сохраняется в базе, но `file_status` меняется на `FATAL`.
    
3. **Оповещение:** Отправляется почтовое уведомление пользователю.
    
4. **Автоочистка:** Сервис очистки автоматически удаляет запись о зараженном файле из БД через 30 дней.
