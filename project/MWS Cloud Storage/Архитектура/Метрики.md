## 2. Слой Netty-ядра (Сетевой мониторинг)

_Инструментируется вручную через `ChannelHandler` и встроенные метрики аллокаторов._

| **Метрика**                | **Тип** | **Теги**                  | **Описание**                                                          |
| -------------------------- | ------- | ------------------------- | --------------------------------------------------------------------- |
| `http.server.requests`     | Timer   | `method`, `uri`, `status` | **RPS и Latency** твоих самописных контроллеров.                      |
| `netty.connections.active` | Gauge   | —                         | Количество текущих открытых TCP-соединений.                           |
| `netty.allocator.memory`   | Gauge   | `type` (direct/heap)      | Мониторинг **Direct Memory**. Критично для Netty, чтобы избежать OOM. |
| `netty.eventloop.usage`    | Gauge   | `executor`                | Насыщенность потоков EventLoop (отношение времени работы к простою).  |

- **`netty.allocator.memory.used` (Gauge)**
    
    - **Что это:** Общий объем памяти, который Netty выделил у системы прямо сейчас.
        
    - **Тег `type`:** `heap` (в обычной куче) или `direct` (вне кучи).
        
    - **Зачем смотреть:** Для твоего облака `direct` — самая важная цифра. Если она растет и не падает после загрузки файла, значит, ты где-то теряешь буферы.
        
- **`netty.allocator.memory.pinned` (Gauge)**
    
    - **Что это:** «Залоченная» память. Это буферы, у которых `refCnt > 0`.
        
    - **Зачем смотреть:** Если это число растет — это прямой индикатор **утечки памяти**. Значит, твои `retain()` не сбалансированы с `release()`.
        
- **`netty.allocator.pools.chunks` / `pages`**
    
    - **Что это:** Технические детали того, на сколько кусков Netty нарезал память для переиспользования. Помогает понять уровень фрагментации.

- **`netty.eventloop.executor.tasks.pending` (Gauge)**
    
    - **Что это:** Количество задач, которые стоят в очереди на выполнение в `EventLoop`.
        
    - **Зачем смотреть:** В идеале тут должен быть **0**. Если число растет, значит, твой код (или `uploadService.uploadPart`) слишком долго блокирует поток, и новые запросы просто не успевают обрабатываться.
        
- **`netty.eventloop.executor.waiting.tasks`**
    
    - **Что это:** Похоже на предыдущую, но часто специфична для конкретных реализаций экзекуторов. Показывает затор в планировщике.

## 3. Бизнес-слой (Critical Path & FSM)

_Самый важный раздел. Реализуется внутри `StorageRepositoryWrapper` и через шедулеры._

### Операционные метрики (Враппер)

- **`storage.operation.duration` (Timer)**
    
    - **Теги:** `operationType` (UPLOAD, DOWNLOAD, DELETE, CHUNK_UPLOAD), `status` (SUCCESS, ERROR).
        
    - _Зачем:_ Видеть реальное время работы с облаком с учетом всех ретраев.
        
- **`storage.retry.total` (Counter)**
    
    - **Теги:** `operationType`, `exception`, `severity`.
        
    - _Зачем:_ Считать «эффективность» инфраструктуры. Большое число ретраев при успехе операций сигнализирует о проблемах с сетью.
        

### Метрики данных (Бизнес-логика) — **NEW**

- **`storage.files.status.count` (Gauge)**
    
    - **Теги:** `state` (PENDING, PROCESSING, READY, FATAL, DANGEROUS).
        
    - _Зачем:_ Мгновенный срез состояния всех файлов в системе. Рост `FATAL` — повод для ручного разбора.
        
- **`storage.payload.size.bytes` (Distribution Summary/Histogram)**
    
    - **Теги:** `operation` (UPLOAD).
        
    - _Зачем:_ Понимать распределение размеров файлов (сколько мелких, сколько гигантов). Это критично для настройки тайм-аутов S3.
        
- **`storage.upload.chunks.active` (Gauge)**
    
    - —
        
    - _Зачем:_ Сколько чанковых сессий сейчас открыто. Позволяет оценить нагрузку на `ChunkedUploadPartEntity`.
        
- **`storage.cleanup.stale.files` (Counter)**
    
    - —
        
    - _Зачем:_ Сколько «протухших» или опасных файлов было удалено шедулером за последний цикл.
