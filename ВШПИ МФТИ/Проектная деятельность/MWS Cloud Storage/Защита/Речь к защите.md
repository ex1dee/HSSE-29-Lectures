##### 2. Цель проекта (10-45с)
Целью нашего проекта является создание **облачного хранилища файлов**, альтернативы Google Drive или Яндекс.Диска, но с важным преимуществами: предоставление **простого и понятного API, системы тегов, а также прозрачных и гибких тарифных планов**.

Кроме того, мы поставили перед собой еще одну цель: не просто создать очередное хранилище, а глубоко изучить, как устроены масштабируемые файловые сервисы изнутри.

___
##### 3. Проблемы проекта

Мы решаем 4 основные проблемы пользователей:

1. **Безопасность и контроль данных** — пользователь получает собственное защищённое пространство
2. **Упрощение совместной работы** — возможность управлять доступом к файлам и папкам для других пользователей
3. **Доступность файлов с любого устройства** — загрузил файл с ноутбука, открыл с телефона — всё работает через единое API
4. **Структурирование данных** — система папок, тегов и поиска помогает организовать даже большой объём файлов.

___
##### 4. Что реализовано (58с-1м21с)
На текущем этапе мы реализовали полный цикл работы с файлами:

Во-первых, **загрузку и скачивание файла** с поддержкой как обычной, так и чанковой передачи для больших файлов
Во-вторых, **полноценную работу с директориями** — создание, перемещение, удаление папок
В-третьих, **систему метаданных** — теги, уровни доступа и переименование файлов

Также реализована **полная система аутентификации** с регистрацией, JWT-токенами и их ротацией; добавлено **управление учетной записью пользователя** и начата разработка **веб-интерфейса на React**.

___
##### 5. Распределение задач (1м21с-1м41с)

Здесь вы можете увидеть распределение задач между членами команды по спринтам.  В основном мы придерживались такому разделению: я отвечал за репозитории, Сергей — за контроллеры, Настя — за сервисы. Такое разделение позволило нам работать параллельно и не мешать друг другу — каждый фокусировался на своём слое.

___
##### 6. High-level architecture (1м41с-2м2с)

На верхнем уровне архитектуры мы видим слой backend, который реализует всю бизнес-логику и предоставляет REST API клиентам, а также два хранилища — PostgreSQL для метаданных и пользователей и MinIO для файлов. Клиенты — например, Postman или веб-интерфейс — взаимодействуют с системой только через REST API

___
##### 7. Стек технологий (2м2с-2м35с)
Для реализации архитектуры мы выбрали следующий стек:

1. Backend на **Java**
2. **MinIO** – как S3-совместимое хранилище для файлов. Его выбрали за простоту развёртывания и надёжность
3. **PostgreSQL** – работаем с ней через **JDBC**
4. **Netty** – для асинхронной обработки HTTP-запросов
5. **JWT** – для аутентификации и генерации токенов
6. **Docker**  – для контейнеризации и развёртывания
7. **TestContainers** – для интеграционных тестов с реальными БД и MinIO
8. **React, JS и CSS** – для веб-интерфейса

___
##### 8. Схема БД (2м35с-2м56с)
Мы спроектировали базу данных из трёх основных таблиц: пользователи, файлы и refresh-токены. Файлы и токены привязаны к пользователю. 

Кроме того, файлы и папки хранятся в одной таблице — различаются флагом is_directory. Хранить их вместе **проще для разработки** и **быстрее для запросов** — все операции над деревом папок делаются в одной таблице. Но в будущем мы разделим эти сущности на две таблицы.
