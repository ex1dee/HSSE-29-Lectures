### Проблема расширения поиска

Обычная Дейкстра тратит ресурсы на проверку узлов, которые находятся «позади» или «сбоку» от старта. Это неэффективно, если мы знаем координаты цели. $A^*$ решает это, добавляя «предчувствие» того, в какой стороне находится выход.

___

### Эвристика ($h[v]$)

Это функция-подсказка. Она оценивает примерное расстояние от текущей вершины $v$ до цели $t$.

- **$h[v] = \rho(v, t)$**: Чаще всего это просто Евклидово расстояние по прямой.
    

#### Допустимая эвристика ($h[v] \leq dist(v, t)$)

Это **главное правило**. Эвристика не должна «оптимистично» занижать реальное расстояние. Она всегда должна быть **меньше или равна** реальному кратчайшему пути.
    

#### Монотонная (консистентная) эвристика ($h[u] \leq h[v] + w_{uv}$)

Это «усиленная» версия допустимой эвристики. Она означает, что при переходе из $u$ в $v$ наша оценка до цели не может уменьшиться больше, чем на вес ребра между ними.

- Если эвристика монотонна, то $A^*$ гарантированно найдет кратчайший путь с первого раза
    

___

### Итоговая функция: $f(v) = dist[v] + h[v]$

Это то, по чему теперь сортируется `PriorityQueue`:

- $dist[v]$ (или $g(v)$) — сколько мы **уже прошли** от старта.
    
- $h[v]$ — сколько нам **примерно осталось** до финиша.
    
- **$f(v)$** — общая ожидаемая длина пути.

___

### Код

```java
// 1. Изменяем компаратор очереди: теперь сортируем по (dist + эвристика)
// В коде это часто называют f = g + h
PriorityQueue<Node> pq = new PriorityQueue<>(
    Comparator.comparingInt(a -> (dist[a.id] + heuristic(a.id, target)))
);

// ... внутри цикла while ...

for (Edge edge : adj.get(u)) {
    int v = edge.to;
    int weight = edge.weight;
    
    if (dist[u] + weight < dist[v]) {
        dist[v] = dist[u] + weight;
        
        // 2. В очередь кладем узел, но его приоритет 
        // будет рассчитан автоматически компаратором выше
        pq.add(new Node(v, dist[v])); 
    }
}
```
