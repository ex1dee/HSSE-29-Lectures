Это набор правил того, как программисту организовать написание кода серверного приложения, чтобы: 
- Все системы легко обменивались данными
- Легко было масштабировать

При взаимодействии клиента с сервером запросы и ответы должны быть определённого формата. Эти форматы определяются протоколом HTTP.

##### HTTP - Hyper Text Transfer Protocol
Когда мы набираем URL-адрес в браузере, мы тем самым отправляем запрос GET на указанный сервер. После этого сервер отвечает HTTP-ответом, содержащим данные в формате HTML (Hyper Text Markup Language). Браузер получает этот HTML-код и отображает его на экране.

**Ресурс** - ключевая абстракция, на которой концентрируется протокол HTTP. Это какая-либо информация или сущность, имеющая уникальный идентификатор - URI.
*Примеры ресурсов:* если мы пишем приложение для управления задачами, то конкретный пользователь, конкретная задача, список задач будут в ней ресурсами.
*Примеры URI:* 
- Создать пользователя: `POST /users`
- Удалить пользователя: `DELETE /users/1`
- Получить всех пользователей: `GET /users`
- Получить одного пользователя: `GET /users/1`

###### Компоненты HTTP:
**Структура запроса:**
- Строка запроса (request line) - определяет тип сообщения
- Заголовки запроса (header fields) - характеризуют тело сообщения, параметры передачи и прочие сведения
- Тело сообщения (body) - необязательно

**Структура ответа:**
- Строка состояния (status line): код состояния, сообщение о причине
- Поля заголовка ответа (header fields)
- Дополнительное тело сообщения (body)



##### Преимущества REST:
- Повышение производительности
- Упрощение архитектуры
- Способность к изменениям
- Переносимость
- Отслеживаемость
- Надёжность

##### Требования к архитектуре REST:
1. **Модель клиент-сервер.** Важно разграничить потребности клиента и сервера. Тогда можно будет повысить переносимость кода клиентского интерфейса на другие платформы и упростить серверную часть.

2. **Отсутствие состояния.** В период между запросами клиента никакая информация о состоянии клиента на сервере не хранится. Соответственно, все запросы от клиента нужно сформировать таким образом, чтобы сервер получал из них всю необходимую информацию для получения запроса. 

	Состояние сессии при этом сохраняется на стороне клиента. Клиент инициирует отправку запросов, когда он готов (возникает необходимость) перейти в новое состояние.

	Во время обработки запросов клиент находится в переходном состоянии.

3. **Кэширование.** Клиенты и промежуточные узлы могут выполнять кэширование ответов сервера. Ответы сервера должны иметь обозначение (явное или неявное) как кэшируемые/некэшируемые для того, чтобы клиенты в ответ на последующие запросы не получали устаревшие или неверные данные.
	Если правильно использовать кэширование, можно (хотя бы отчасти) устранить некоторые проблемы клиент-серверного взаимодействия.

4. **Единообразие интерфейса.** Унифицированные интерфейсы позволяют каждому из сервисов развиваться независимо. 
	Требования к унифицированным интерфейсам:
	- *Идентификация ресурсов.* Все ресурсы идентифицируются в запросах (например, при помощи URI)
